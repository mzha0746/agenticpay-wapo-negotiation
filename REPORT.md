# Bezos vs. Graham: AgenticPay-style negotiation for The Washington Post

**Setup in one line:** 1 buyer × 1 seller × 1 product (AgenticPay "Single Buyer, Single Product, Single Seller", Table 11). Both agents run on the same LLM, Qwen3-4B-Instruct-2507, served offline. The buyer's secret max is **$350M** and the seller's secret min is **$200M**. There are 10 independent runs per condition.

## Headline results

| Condition | What changes | Deal rate | Avg final price ($M, deals only) | Range | Avg rounds / run |
|---|---|---|---|---|---|
| `paper_verbatim` | Tables 14/15 word-for-word, generic "Buyer"/"Seller" | 40% (4/10) | 307.5 | 290–340 | 17.3 |
| `paper_default` | + one shared "write a natural-language message" line (see §1.4) | 0% (0/10) | – | – | 20.0 |
| **`persona_original`** (baseline for Part 2) | + public facts about Bezos, Graham and the Post | 40% (4/10) | **331.2** | 320–335 | 18.0 |
| `persona_anchor_evidence` (buyer variant A) | + anchoring / evidence / shrinking-concession instructions | 40% (4/10) | **231.2** | 210–245 | 16.7 |
| `persona_schedule_value` (buyer variant B) | + explicit concession schedule + non-price value trades | **80% (8/10)** | **214.1** | 200–232 | **11.7** |

- **Rounds:** a run that hits the 20-round limit without a deal counts as 20 rounds.
- **Reservation prices:** no deal violated either side's reservation price.
- **Data:** per-run JSON transcripts are in `results/`, and the table is generated by `src/analyze.py`.

**Bottom line:**
- Changing only the buyer's prompt cut the average deal price from **$331M to $214–231M**, which is ~$100–117M of extra buyer surplus.
- Variant B also **doubled the deal rate** (40% → 80%) and roughly halved the negotiation length.
- n = 10 per condition and only 4–8 deals per condition, so treat these as indicative rather than precise estimates. The gap between the baseline and both variants is still far larger than the within-condition spread (std 7.5–15).
- Robustness checks (§5): with only 8 rounds or temperature 0, Variant B's deal rate drops sharply, so its advantage depends on the setting.

## 1. Method

### 1.1 Code base and fidelity to AgenticPay
I cloned `github.com/SafeRL-Lab/AgenticPay` (in `ref/`) and read the paper's HTML (arXiv 2602.06008v1). The current repo has moved on from the paper: it uses JSON contracts, `<mental_model>` blocks, and no `MAKE_DEAL` keyword. So I wrote a small standalone runner that combines two sources:

- **Prompts:** Tables 14 (buyer) and 15 (seller) of the paper, copied verbatim (`src/prompts.py`). Only the `{placeholders}` are filled in.
- **Environment mechanics** copied from the repo's `Task1_basic_price_negotiation.py` and `examples/config.py`:
  - Each round the buyer speaks first, then the seller replies having seen the buyer's message.
  - `max_rounds = 20` and `price_tolerance = 0`.
  - Prices are parsed with the same `### BUYER_PRICE($X) ###` / `### SELLER_PRICE($X) ###` regex.
  - If `seller_price <= buyer_price`, the deal closes at the seller's price.
- **`MAKE_DEAL` protocol (from the paper's prompts):** a party that says `MAKE_DEAL` accepts the counterpart's latest offer.

**Scenario parameters:**
- The seller's initial asking price is $400M. Table 15 requires an `{initial_price}`; the task didn't specify one, so I chose a value above the buyer's max.
- All prices are in millions of USD, and the prompt tells both agents so.
- The product is the set of businesses actually sold in 2013: what was included and excluded comes from the Post Co. announcement, e.g. the HQ building, Slate and Foreign Policy were excluded.

### 1.2 Model / offline inference
- **Model:** Qwen3-4B-Instruct-2507. My test machine is a laptop RTX 4060 with 8 GB VRAM, and the official BF16 weights (~8 GB) don't fit. I used the **Q8_0 GGUF** (`bartowski/Qwen_Qwen3-4B-Instruct-2507-GGUF`, revision `ae44f08`). It is converted directly from `Qwen/Qwen3-4B-Instruct-2507`, and Q8_0 is close to lossless.
- **Serving:** the model ran locally on llama.cpp `llama-server` (build b11724, CUDA 12.4), fully offloaded to the GPU. No network was used at inference time.
- **Swapping the backend:** the runner only talks to an OpenAI-compatible endpoint. `vllm serve Qwen/Qwen3-4B-Instruct-2507` would run the identical experiment on the full-precision weights with no code change.
- **Sampling:** Qwen's recommended settings for the 2507 Instruct model: temperature 0.7, top_p 0.8, top_k 20, max 512 tokens. The repo default is temperature 0, which would make all "10 independent runs" identical.
- **Seeds:** run *i* uses seed *i* in every condition (common random numbers), so differences between conditions are not driven by seed luck.

### 1.3 Conditions
Only the **buyer** prompt differs among the three `persona_*` conditions; the seller prompt is byte-identical across them. `paper_verbatim` and `paper_default` are reference points.

### 1.4 One necessary harness fix (and why it is reported separately)
With the verbatim Table 14/15 prompts, Qwen3-4B answered every turn with **only** the tag, e.g. `### BUYER_PRICE($300) ###`, and never wrote a sentence.
- This held across 3 seeds, for the chat template vs. raw completion, with the format line inline, and with the 150-word line removed.
- With no sentences, the persona facts and any persuasive strategy cannot have an effect.

**The fix:** I added one line to **both** the buyer and seller prompts:
> "Write your reply as a natural-language message to the other party (2-5 sentences) that includes your one price offer tag."

All other conditions include this line. `paper_verbatim` is kept as the purely verbatim reference.

## 2. Part 1 – Public information added to the prompts

### 2.1 How the data was fetched
1. I ran web searches (an LLM-agent web-search tool) for:
   - Graham's staff letter and his reasons for selling;
   - Bezos's 2013 letter to Post staff;
   - the Post's 2012/2013 financials.
2. I fetched the pages below with an HTTP fetch tool, converted them to text, and extracted facts by hand.
3. I tried washingtonpost.com directly and it returned 403 (paywall), so I used Poynter's contemporaneous write-up, which quotes the Post Co. release and both letters.
4. Every fact is stored in `src/facts.py` with a source key, so the prompt text and its citations come from one place.

**Selection rule:** I only used information that was public, or that the person themselves would know, **before** the deal (July 2013). The actual outcome was **deliberately excluded** from both prompts: the price was $250M, and Graham said "I named a price and Jeff agreed to pay it." Otherwise the agents could simply recite history (see §6).

## 3. Part 2 – Buyer prompt variants (seller prompt unchanged)

Diagnosing the baseline transcripts showed three buyer weaknesses:
1. It **anchors high**: the first offer is ~$300M, i.e. 86% of its maximum.
2. It **concedes fast**, then both sides lock into a "fair and balanced" loop a few dollars apart until time runs out.
3. It **never uses the bad public numbers or the seller's non-price motives** as leverage.

Both variants target these weaknesses. They are added as a "NEGOTIATION STRATEGY" block before the final "Now, respond as Jeff Bezos:" line (`src/prompts.py`, `STRATEGIES`).

**Variant A – `anchor_evidence` (qualitative tactics)**
- Open at around $150M and justify it with the public losses, the circulation decline and the excluded HQ building. This is the standard anchoring tactic.
- Frame the asset as a turnaround that needs years of the buyer's own capital.
- Concede in shrinking steps (+20, +10, +5); never split the difference.
- Signal a strong walk-away option (BATNA: "I don't need this deal").
- Private target ≈ $220M; don't say MAKE_DEAL above $250M unless rounds are running out.

**Variant B – `schedule_value` (explicit schedule + value trade)**
- Same evidence-based justification as A.
- **A fixed concession schedule by round:** 150 → 165 → 178 → 188 → 196 → 203 → 209 → 214, then +3 per round, capped at 250.
  - Small LLMs are bad at pacing concessions on their own; a numeric schedule turns pacing into instruction-following, which a 4B model does well.
  - The steps shrink, which signals that the buyer is near its limit.
- **Trade non-price value instead of money.** The public record says Graham cares about stewardship, so the buyer offers things that cost the buyer nothing:
  - keep the publisher and editors;
  - protect newsroom independence;
  - invest long-term in digital;
  - all cash with a fast, certain close for his shareholders.
- Accept as soon as the seller's ask is at or below the scheduled price.

### Results (10 runs each)
| | Baseline `persona_original` | Variant A | Variant B |
|---|---|---|---|
| Deal rate | 40% | 40% | **80%** |
| Avg final price (deals) | $331.2M | $231.2M | **$214.1M** |
| Avg rounds per run | 18.0 | 16.7 | **11.7** |
| Avg buyer surplus per run (350 − price; 0 if no deal) | 7.5 | 47.5 | **108.7** |

The surplus row puts the trade-off in one number. A lower price only helps if a deal happens, and Variant B wins on both price and deal rate.

**What the transcripts show:**
- **Variant B:** the buyer followed the schedule perfectly: 0 of 117 offers were above the scheduled number (`src/check_schedule.py`). The seller conceded along with it (300 → 250 → 225 → …), and in 2 runs the seller went all the way down to its $200M floor.
  - Both failures (runs 6 and 9) ended only $3–5M apart ($232 vs $235; $235 vs $240). The buyer stalled at $232–235 even though the schedule allowed up to $250, and the seller stopped conceding too.
- **Variant A:** the anchoring worked: the seller dropped from $300M to $210–250M. But the free-form concessions again ended in "I'll stay at X" standoffs (6/10 timeouts). The buyer also sometimes **pre-announced its next concession** ("I'll revisit at $180 if…"), which is a tactical leak.
- **Role confusion:** with persona prompts the buyer sometimes addressed the seller as "Jeff" (52 turns in the baseline, 32 in A, 8 in B). The 4B model sometimes mixes up who is who.

## 4. Other observations
- **Prompt brittleness dominates.** One harmless-looking formatting line moved the non-persona deal rate from 40% to 0%. Talking agents justify their last number and then repeat it, so "agreeing" becomes harder. Any comparison between conditions has to hold everything else fixed. That is why I used one fixed seller prompt, common seeds, and the same harness line in every compared condition.
- **No deal broke a reservation price.** There was one stray offer below the floor: a seller ask of $198M in schedule run 2, while its min was $200M; the deal itself closed at $200M.
- **The termination rule matters.** Almost every deal closed by "prices crossed" rather than `MAKE_DEAL`. The 4B models rarely type the keyword, so results depend on the environment's crossing rule.

## 5. Robustness checks: fewer rounds and temperature 0

Do the main conclusions depend on the exact settings? I ran two extra experiments comparing only the baseline (`persona_original`) and Variant B (`persona_schedule_value`), 5 runs each, all other settings unchanged.

### 5.1 Max rounds 20 → 8 (temperature still 0.7)
| | Deal rate | Avg final price (deals) | Avg rounds | Main experiment (20 rounds) |
|---|---|---|---|---|
| Baseline | 60% (3/5) | 335.0 | 6.2 | 40%, 331.2 |
| Variant B | 40% (2/5) | 206.5 | 7.6 | 80%, 214.1 |

- **The baseline closes more often.** It opens at 300 and quickly reaches 335, already close to the seller's ask, so it can agree within 8 rounds, at a high price.
- **Variant B is held back by its fixed schedule.** The schedule only reaches 214 in round 7 (the last round). All 3 failures ended at "buyer 214, seller 225–240": a gap the schedule would have closed with a few more rounds.
- **Implication:** a fixed schedule doesn't adapt its concession speed to the rounds remaining, so it misses feasible deals when time is short. A better design would scale concessions with the rounds left.

### 5.2 Temperature 0.7 → 0 (20 rounds)
| | Deal rate | Avg final price (deals) | Avg rounds |
|---|---|---|---|
| Baseline | 100% (5/5) | 345.0 (all five at 345) | 8.0 |
| Variant B | 20% (1/5) | 209.0 | 17.4 |

- **The baseline's 5 runs are identical:** all closed at 345 in round 8. With temperature 0, repeated runs carry no information, which confirms that using 0.7 in the main experiment (instead of the repo default 0) was necessary.
- **Temperature 0 is not fully deterministic:** Variant B's run 0 differs from the others from the buyer's first message; runs 2–4 are identical and run 1 differs slightly. A likely cause is tiny GPU floating-point nondeterminism (e.g. a different computation order when the server reuses the previous request's cache) flipping a near-tie between tokens. I have not fully verified this.
- **Variant B mostly fails:** in the 4 failures the seller holds firm at 250 while the buyer follows the schedule to 244–247, and the schedule's cap is also 250. Without sampling noise the seller never makes the occasional extra concession, so talks stall. So part of Variant B's 80% deal rate in the main experiment came from sampling randomness.

### 5.3 Takeaway
Variant B is best at 20 rounds and temperature 0.7, but its advantage shrinks or reverses with fewer rounds or temperature 0. The main result should be read as "effective in this specific setting", not "this prompt is better in general", which directly supports point 4 of the next section (small, setting-sensitive samples). Data are in `results_rounds8/` and `results_temp0/`.

## 6. What could go wrong when using this to analyze a real-world setting
1. **The model isn't the person.** "You are Jeff Bezos" plus ten facts produces a generic polite negotiator who writes "fair and balanced" in every turn. The real deal was short: Graham named a price and Bezos accepted. Nothing in the simulation reproduces relationships, trust, reputation or face-to-face dynamics.
2. **Data leakage / memorization.** The sale is famous and almost certainly in the training data ($250M). The model may anchor on the true price even when we hide it, which would make the simulation look "accurate" for the wrong reason. Conversely, adding the outcome to the prompt would just make it copy the answer. For real forecasting you would need events after the training cutoff, or counterfactual tests (e.g. change the reservation prices and check that the outcomes move).
3. **Made-up numbers drive the result.** The $350M and $200M reservations and the $400M opening ask are assumptions, not historical facts. The outcome is largely determined by them and by the round limit, not by "Bezos" or "Graham".
4. **Small and fragile samples.** Ten runs per arm, a 4B quantized model, and one sampling configuration. Results moved a lot with tiny prompt edits (§4). The conclusions might not survive another model, another temperature, or a different deal-closing rule.
5. **Asymmetric optimization is unrealistic.** We tuned only the buyer against a fixed, naïve seller. A real Graham (advised by Allen & Co.) would adapt. Prompt tactics that exploit a small model's compliance, like "follow this schedule", say little about what works against people.
6. **The facts are selective.** I chose which facts to include, and that choice frames the agents. Emphasizing losses favors the buyer; emphasizing legacy favors the seller. Some sources are secondary (Wikipedia, press), and the most authoritative one (the Post itself) was paywalled.
7. **Single-issue simplification.** The real deal involved non-price terms: asset scope, working-capital adjustments, leadership retention, editorial independence, and Graham's non-financial motives. Collapsing all of that into one price misses why the deal happened.
8. **Ethics and privacy.** These are simulations of real, living people. Generated transcripts could be mistaken for real statements or misused, so outputs should be clearly labeled as fiction and not attributed to them.
9. **Evaluation artifacts.** The agents' rhetoric includes no real information exchange, and termination depends on regex parsing. Parser edge cases (a stray tag, a missing tag) can decide outcomes.

## 7. Reproduce
```bash
# 1. model server (any OpenAI-compatible server works)
llama-server -m Qwen3-4B-Instruct-2507-Q8_0.gguf -ngl 99 -c 12288 --port 8080
#    or: vllm serve Qwen/Qwen3-4B-Instruct-2507 --port 8080
# 2. experiments (resumable; 50 runs ≈ 1.5 h on a laptop RTX 4060)
cd src && python negotiate.py --runs 10 --out ../results
# 3. tables / diagnostics
python analyze.py ../results
# robustness checks (§5)
python negotiate.py --runs 5 --conditions persona_original persona_schedule_value --max-rounds 8 --out ../results_rounds8
python negotiate.py --runs 5 --conditions persona_original persona_schedule_value --temperature 0 --out ../results_temp0
cd ../results && python ../src/check_schedule.py && cd ../src && python offer_violations.py
```
